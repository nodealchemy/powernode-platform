# System Frontend — Linkable References + Consistent Index UX (Proposal)

> **Status:** review gate (read-only audit complete; no code changed yet).
> Generated by the `entity-reference-audit` workflow (14 agents). This is the artifact to review
> before the apply run. Companion machine-readable data: `/tmp/audit/{manifest,gaps,surfaces,refs}.json`.

## Why this exists

The system-extension frontend renders **115 object references, 98 of them dead text** (a `node`'s
template, a module's parent/category/platform, a volume's region, a task's polymorphic `operable`, …),
and uses **mixed list layouts** (24 plain index-tables, 15 expandable, 26 custom panels, 13 inline-lists,
1 card-grid). The goal: make every reference clickable → the target object's detail surface, and converge
indexes on one pattern. The mechanism is built **once in core `shared/`** (`EntityLink` + registry +
global modal host, mirroring `featureRegistry`) and reused for core + other extensions next.

## Recommended standard (from the audit)

The audit's recommended target is an **expandable-row index table** for every object index: an item's own
scalar/JSON detail expands inline (no modal round-trip); **cross-references to other objects are always
links** opening the target's detail surface; detail **modals are kept only for editors/management consoles
and forms**; dashboards, topology/graph canvases, composers, and one-time secret-reveal lists stay as-is.

## Recommended standard

**Default for every object index surface: an expandable-row index table.**

- Desktop renders a `ResponsiveListContainer.Desktop` table; the leading column is a chevron disclosure. The expanded region shows **that object's own scalar/JSON detail inline** (description, status detail, timestamps, IPs, specs, config) — no modal round-trip for an item's own fields.
- Mobile renders `ResponsiveListContainer.Mobile` cards with the same tap-to-expand.
- **Cross-references to other object types are always links** that open the *target* object's detail modal/drawer (e.g. a node row's template cell opens `TemplateDetailModal`; an instance's holder opens that peer's surface). Never plaintext IDs, never the parent's modal showing a foreign object read-only.
- Bulk/lifecycle actions live in the row's action cell or the `PageContainer` header — never inside page body content.

**When a detail *modal* is still allowed:** only for **create/edit forms** and for **management consoles that mutate child collections** (multi-tab surfaces with per-tab CRUD — SDWAN network 7-tab, Provider regions/connections, Federation peer drawer). These are not "view this object's fields"; they are editors. Keep them, but their *read-only field display* should still be reachable by expanding the row.

**Justified exceptions (stay cards / custom panel):**
- Dashboards, topology/graph canvases, real-time monitors, and visual composers (SystemOverview, SDWAN topology, OVN switch view, FleetDashboard, TemplateComposer, flow/BGP telemetry). Spatial or live-streaming data is not tabular.
- Hub/page organizers that only host tabs (no rows of their own).
- Secret-reveal "shown once" lists where expansion would imply re-display.

**No High-effort surfaces** — every transformation is either (a) adding a chevron + inline detail region to a list already on `ResponsiveListContainer` (Low–Med), (b) converting a card-grid/custom-panel into the Desktop/Mobile table split the container already supports (Med), or (c) relabeling plaintext cross-reference cells/IDs as links to the target object's existing modal/drawer (Low).

**Cross-cutting workstream (counts across all domains):** the single highest-leverage change is a shared **`<CrossRefLink objectType=… id=… label=…>`** helper that routes any cross-reference cell to the target object's detail surface. ~40 reference sites in the audit are plaintext/count today; centralizing the link behavior makes most "link the X cell" sub-tasks one-line edits.

**Total surfaces audited: 95** (includes the Hubs & Pages re-audit duplicates). Distinct files/components ≈ 71. Net new expandable-row conversions: ~28 leaf lists; demoted-to-management modals: 6 (Node/Template/Module Info tabs, Provider/Volume/Pool detail); pure exceptions retained: ~26; forms/wizards retained: ~22.

Key grounding facts: `extensions/system/frontend/src/features/system/components/shared/ResponsiveListContainer.tsx` already provides `Filters`/`Desktop`/`Mobile`/`Body` slots + infinite scroll, but **no built-in expandable-row mechanism** — `NodeList`/`TemplateList` implement disclosure themselves over the `Desktop` slot, so that is the template to copy. `ProviderList` is the only leaf list using the `Body` (card-grid) slot rather than the table split.
