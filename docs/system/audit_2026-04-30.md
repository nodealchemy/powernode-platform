# System Extension — Senior-Engineer Audit (2026-04-30)

> **Audit type.** Read-only review. No code changes were made as part of this audit.
> **Status.** Findings only. Prioritized cleanup table at the bottom is recommended order, not committed work.

---

## Context

**Why this audit.** The `extensions/system/` extension absorbed a large legacy codebase (`powernode-server` + `powernode-agent`) into a Rails 8 / React / Sidekiq stack. Recent sprints normalized service returns to `Runtime::Result`, renamed `System::Operation → System::Task`, rewrote `AzureProvider` against faraday 2, added `Providers::CatalogSyncService`, added template export, and added a nested PuppetResource form. The extension now has ~7.2k LOC of backend code and ~16k LOC of frontend. A senior-engineer pass is in order to surface structural problems, duplication, performance bottlenecks, and maintainability risk that have accumulated.

**Out of scope.** Not auditing: `extensions/system/spec/` factories or fixture state; legacy `powernode-server`/`powernode-agent` repos; cross-extension concerns. Pre-existing test failures (39 of 872 examples) are reported but not reclassified as audit findings.

## Architecture Overview

**Three runtimes, four controller surfaces, one AASM truth.**

```
                 OPERATOR JWT          WORKER TOKEN         INSTANCE TOKEN
                       │                    │                     │
                       ▼                    ▼                     ▼
              api/v1/system/*    api/v1/system/worker_api/*    api/v1/system/node_api/*
              (operator CRUD)    (worker dispatch + reports)   (running instances)
                       │                    │                     │
                       └──────────┬─────────┴─────────────────────┘
                                  ▼
                         System::Task (AASM)
                         pending → scheduled → running → complete | failed | aborted | cancelled
                                  │
              after_commit on create ─┐
                                      ▼
                      worker/jobs/SystemExecuteTaskJob (event-driven, no polling)
                                      ▼
                      POST /api/v1/system/worker_api/tasks/:id/execute
                                      ▼
                      System::ExecutionDispatcher.run
                        - claims via AASM start! (FOR UPDATE SKIP LOCKED in TaskDispatcher)
                        - 16-command lookup table → System::Runtime::*
                                      ▼
                      Runtime services (pure Ruby) wrap core services
                                      ▼
                      System::ProvisioningService / SshExecutionService / VolumeManagementService / ...
                        all return System::Runtime::Result
                                      ▼
                      Provider adapters (AWS, Azure, GCP, OpenStack, Mock) via Providers::Registry
```

**Frontend.** 16 pages registered in `register.ts`, fed by a single 984-line `systemApi.ts` module and a `SystemChannel` ActionCable subscription (`useSystemWebSocket`).

## Structural Problems

### S1. Routes/controller drift on `provider_availability_zones` (HIGH)
- **Controller**: `app/controllers/api/v1/system/provider_availability_zones_controller.rb:7-10` reads `params[:provider_id]` and `params[:region_id]`.
- **Routes**: `config/routes.rb:59` declares it flat (`resources :provider_availability_zones`), so neither parent ID is supplied. Same shape as the puppet_resources bug fixed earlier in this sprint.
- **Effect**: Endpoint silently 500s on `set_provider`/`set_region` when invoked.

### S2. `AzureProvider` interface incompatibility with `BaseProvider` (HIGH)
- `AzureProvider#restart_instance` (line 138) — base contract is `reboot_instance`. `InstanceControlService#execute_cloud_action` happens to call `restart_instance` so this works there, but other callers expecting `reboot_instance` will break against Azure.
- `AzureProvider#detach_volume(volume_id, instance_id)` (line 477) — base contract is `detach_volume(volume_id, force: false)`. Signature mismatch breaks polymorphism; `VolumeManagementService#detach` calls `provider_adapter.detach_volume(volume.cloud_volume_id, force: force)` which fails against Azure with `ArgumentError`.
- `AzureProvider` returns `{ success: false, error: ... }` for failures (line 838) where AWS/GCP/OpenStack raise typed exceptions (`AuthenticationError`, `RateLimitError`, etc.). Callers handling Azure must inspect a hash, not catch — an inversion of the contract.

### S3. Stubbed services that return success without doing the work (HIGH)
- `ImageCreationService:216, 240, 288, 310` — logs `"Would create..."` and returns success. Nothing creates an actual `.img`, ISO, AMI, or VMDK. Any caller depending on a real artifact reads from a non-existent path on success.
- `ModuleBuildService:112` — `"Would extract module data to #{src_dir}"`. The build pipeline thinks it succeeded; later stages run on an empty staging dir.
- `ModuleCommitService:150` — `"Would extract module data"`; `:354` — `"Would apply mask to..."`.
- `SshExecutionService` `mock_ssh_response` (line 169-170) — returns `exit_code: 0, stdout: "Mock execution of: <cmd>"` **for every command** when `SYSTEM_SSH_ENABLED=false`. In a misconfigured environment this silently green-paints failed deploys.

### S4. Worker/operator serialization divergence (MEDIUM)
- Operator: `Api::V1::System::TasksController` uses `::System::TaskSerializer` consistently.
- Worker API: `Api::V1::System::WorkerApi::TasksController` (lines 262-285) inlines `serialize_task` and `serialize_operation_full` with hand-rolled hashes. Same domain object, two shapes — a worker that round-trips a task back to the operator surface will see different fields.

### S5. Model validations missing scope (MEDIUM)
- `System::ProviderInstanceType` (line 15): `validates :name, presence: true` — no uniqueness scope. The model has both `account_id` and `provider_id`; the natural scope is `[account_id, provider_id]`.
- `System::ProviderAvailabilityZone` (line 15): same shape; should scope to `provider_region_id`.
- `System::ProviderRegion` (line 22): should scope to `[account_id, provider_id]`.
- `System::ProviderVolume:18` uses non-conventional FK `:volume_id` for snapshots; Rails convention would be `:provider_volume_id`. Cosmetic, but breaks ActiveRecord auto-detection.

### S6. `SystemTaskReaperJob` is not scheduled (MEDIUM)
- The job exists at `worker/app/jobs/system_task_reaper_job.rb:25` and is the only safety net for tasks stuck in `pending` (>5 min) or `running` (>60 min). No `sidekiq_scheduler.yml` entry exists. The dispatcher is event-driven via `after_commit`, so any operation that misses its enqueue (Redis blip, worker crash mid-publish) sits forever without the reaper.

## Duplicated Code

### D1. `get_provider_connection_for_region` (HIGH)
- `CloudSyncService:179-187` and `VolumeManagementService:248-256` — identical 7-line query (filter by provider, account fallback via OR, status connected, first). Should live on `Providers::Registry` or a shared concern.

### D2. Cloud-credential extraction (HIGH)
Each adapter parses `ProviderConnection` differently and there's no shared parser:
- AWS (`aws_provider.rb:444-452`) — `Aws::Credentials.new(connection.access_key, connection.secret_key)`
- Azure (`azure_provider.rb:607-621`) — `tenant`, `access_key` (client_id), `secret_key`
- GCP (`gcp_provider.rb:725-734`) — JSON parse of `secret_key` as service-account JSON
- OpenStack (`openstack_provider.rb:516-524`) — hash from `access_key`, `secret_key`, plus `connection.config` keys

A `BaseProvider#credentials` template method with provider-specific subclass overrides would unify this.

### D3. Status normalization scattered across adapters (MEDIUM)
Five separate `STATUS_MAP` constants — AWS (6 states), Azure (8, with `PowerState/` and `ProvisioningState/` prefixes), GCP (8), OpenStack (10), Mock (passthrough). Each adapter implements its own `normalize_status`. Platform target states are documented in `BaseProvider:19-30` but no shared mapper enforces parity. Semantic drift: Azure maps `deallocating → stopping`, GCP maps `SUSPENDING → stopping`, but billing/state-retention behaviors differ — the platform consumes both as "stopping".

### D4. Provider-error translation patterns (MEDIUM)
- AWS (line 549-567), GCP (line 905-922) catch typed SDK exceptions and re-raise as `BaseProvider::ProviderError` family.
- OpenStack (line 589-605) string-matches HTTP codes (`"401"`, `"429"`) instead of catching exceptions.
- Azure (line 838-845) returns failure hashes instead of raising. Callers can't `rescue` consistently.

### D5. Frontend list/form/detail trio repeated 8× (MEDIUM)
For each of `nodes`, `operations` (now tasks), `providers`, `templates`, `modules`, `volumes`, `puppet`, `scripts`:
- Filter + dropdown state hooks (e.g., `OperationList:84-88`, `NodeList:84-88`, `TemplateList`) — same `useState<string|null>` for `dropdownOpen` and structurally identical filter shape.
- Mobile-cards + desktop-table dual rendering (e.g., `OperationList:314+`, `NodeList:261-379`, `TemplateList:287-418`) — same pattern, copy-pasted.
- Fetch + refresh + loading triplet (`useState(loading)`, `useState(refreshing)`, `useCallback(fetch)`) — same shape, no shared `useResourceList()` hook.

A `ResponsiveListContainer` + `useResourceList` extraction would shrink each list component by 100-150 lines.

### D6. Provider Registry try/rescue wrapper (LOW)
Pattern repeated in 8+ services:
```ruby
provider_adapter = begin
  Providers::Registry.for_*(...)
rescue Providers::Registry::UnknownProviderError => e
  return Runtime::Result.err(error: e.message)
end
```
A `Registry.resolve_or_result(...) { |adapter| ... }` block helper would remove the boilerplate.

## Performance Bottlenecks

### P1. No pagination in any cloud `list_instances` (HIGH)
AWS/Azure/GCP/OpenStack all fetch the full list in a single API call. AWS EC2 caps at 1000/page by default, GCP at 500, Azure at varying per resource type. `CloudSyncService#sync_region_instances` (line 145+) and `Providers::CatalogSyncService.sync_for` will silently truncate beyond the page size on real accounts. Symptoms: "instance disappeared from sync" reports that aren't actually deletions.

### P2. Sequential SSH inside maintenance task loops (HIGH)
`InstanceMaintenanceService` and `NodeMaintenanceService` loop over instances and run SSH commands one at a time. With N=20 running instances and a 30-second SSH timeout, a single `task_health_check` round can take 10 minutes. The Sidekiq job timeout (60 min, configured per queue) would eventually fire, but in the meantime nothing else in the `system` queue moves.

### P3. WebSocket broadcast amplification on Task updates (MEDIUM)
`System::Task#broadcast_update` (line 219) fires on `after_commit` for every status or progress change. `update_progress!(20, ...)` then `update_progress!(50, ...)` each broadcast to all subscribed clients — every operator on the system receives 1 message per progress tick across all running tasks. Throttling/coalescing is absent.

### P4. `mock_ssh_response` masks misconfigurations as success (MEDIUM)
`SshExecutionService:169-170` returns `exit_code: 0` for every command when SSH is disabled. This is fine for CI but turns a misset env var into a silent green build that does nothing.

## Maintainability Risks

### M1. `systemApi.ts` is a 984-line, 107-method monolith (HIGH)
- `frontend/src/features/system/services/systemApi.ts` — single object, no domain segregation.
- Response shapes inconsistent: some methods return `extractData(response).foo` (line 150), others wrap in `{nodes, meta}` (line 145), others return bare arrays. TypeScript can't catch the difference because most methods type the response as `any`.
- Splitting into per-feature files (`templatesApi.ts`, `providersApi.ts`, etc.) and tightening response types would surface latent bugs.

### M2. `useOperationPolling` (311 LOC) and `useSystemWebSocket` (372 LOC) under-adopted (MEDIUM)
- `useOperationPolling.ts` / `useTasks` — **zero callers** in the codebase. Dead.
- `useSystemWebSocket` — used by `NodeDetailModal:77` and `TemplateDetailModal:86` only. `OperationsPage`, `OperationList`, every other list page lacks live updates. Inconsistent UX: detail views are real-time, list views are static.

### M3. AzureProvider test spec is stale (HIGH — already known)
- 27 of the 39 pre-existing failures sit in `spec/services/system/providers/azure_provider_spec.rb`. The spec mocks `instance_double` for SDK clients that no longer exist (Azure was rewritten to faraday-REST). Spec/source ratio: 0.23 — lowest of all adapters.
- Other ratios: AWS 0.50, GCP 0.20, OpenStack 0.28, Mock 0.74. GCP is the next-weakest.

### M4. `shared_examples.rb` is shallow (MEDIUM)
- `spec/services/system/providers/shared_examples.rb` (lines 6-67) — a `respond_to?` smoke test for 16 methods. No behavioral assertions. Line 64 has a `pending` block that's been there for the duration of the rewrite. Adapters can drift in semantics indefinitely without a behavioral shared spec catching it.

### M5. Inconsistent error contract between adapters (MEDIUM)
Per D2/D4 above — Azure breaks the "raise on error" contract with hash returns; OpenStack pattern-matches strings. Callers cannot `rescue Providers::BaseProvider::ProviderError` and trust they've handled all paths.

### M6. Stubbed services indistinguishable from working ones (HIGH)
Per S3 above — `ImageCreationService`, `ModuleBuildService` stage_prepare, `ModuleCommitService` mask logic all log "Would..." and return `success: true`. There is no `service.real?` flag, no `Rails.logger.warn`, no startup banner, no spec matcher. A future engineer will spend a debugging session figuring out why a "successful" image-creation operation produced no image.

### M7. `FileObject` association referenced but model missing (MEDIUM)
- `System::NodeArchitecture` declares associations to a `FileObject` model (`kernel_file_object`, `ramdisk_file_object`, `image_file_object`).
- `FileObject` is not defined in the system extension — 11 of the 39 pre-existing test failures are `Missing model class FileObject`. Either the platform needs a `FileObject` model, or the associations should be removed/renamed to a model that exists. The associations are read by `boot_image_*` methods on the model, so removing them is breakage.

### M8. `NodeInstance#can_*?` predicates referenced in specs but not defined (LOW)
`spec/integration/system/node_provisioning_integration_spec.rb:109-119` asserts `instance.can_stop?`, `can_start?`, `can_reboot?`, `can_terminate?`. These methods don't exist on `NodeInstance`; AASM only generates `may_start?` etc. The spec has been red since written. Either the predicates should be added (delegating to `may_*?`) or the spec should be reworked.

### M9. Dispatch chain has no observability hook (LOW)
`ExecutionDispatcher.run` has Rails.logger calls but no metric emission, no event bus publish, no Sidekiq job tagging. When a task fails the only audit trail is the task's own `events` array. Cross-task analytics (failure rate by command, p95 dispatch latency) require querying the database directly.
